Lab 2 : le tournoi des mutants

Un collègue a fait écrire les tests du calcul de prix par un assistant. Vingt tests, tous verts, toutes les branches couvertes. Est-ce que ces tests détectent vraiment une erreur ? Le mutation testing répond : il introduit des bugs dans le code et regarde si les tests les voient.

Le principe

Stryker modifie le code, une petite erreur à la fois : un >= devient >, un + devient -, une constante change. Chaque version modifiée est un mutant.

  • Si un test échoue, le mutant est tué : vos tests ont vu l'erreur.
  • Si tous les tests passent, le mutant survit : vos tests n'auraient pas vu ce bug.

Le score de mutation est la part de mutants tués. C'est une mesure bien plus honnête que la couverture.

1. Mesurer le point de départ (5 min)

Le module src/TicketRush.Domain/Pricing.cs calcule les prix. Ses tests sont dans tests/TicketRush.UnitTests/PricingTests.cs : une vingtaine, qui passent tous et couvrent toutes les branches. Lisez-les rapidement : auriez-vous accepté cette suite en revue de code ?

cd tests/TicketRush.UnitTests
dotnet tool restore
dotnet stryker

Notez le score affiché pour Pricing.cs et annoncez-le au formateur : il est reporté au tableau.

2. Lire le rapport (10 min)

Ouvrez le rapport HTML (StrykerOutput/…/reports/mutation-report.html). Chaque mutant survivant y est montré dans le code. Choisissez-en trois et, pour chacun, répondez en une phrase : quel bug réel ce mutant représente-t-il, et quel test existant aurait dû le voir ?

3. Le tournoi (25 min)

Objectif : tuer le plus de mutants survivants possible. Écrivez chaque test d'après la règle métier (ci-dessous), pas d'après le code. Attention : le code n'est peut-être pas juste. Si un test écrit d'après la règle échoue, ne le modifiez pas : vous avez trouvé un bug. Corrigez Pricing.cs, relancez les tests, et notez-le. À la main, ou en guidant l'IA avec le rapport Stryker : donnez-lui le mutant précis et la règle métier, pas seulement le code. Pour chaque mutant tué, notez dans un fichier notes.md :

  • le mutant (ligne, modification) ;
  • pourquoi la suite du collègue ne le voyait pas ;
  • la règle métier ou la frontière que votre test vérifie désormais.

La règle métier du prix (elle fait foi, pas le code) : prix de base Fosse 65 €, catégorie 1 89 €, catégorie 2 49 € ; tarif réduit -20 %, enfant -50 % (interdit en fosse) ; frais de service 1,50 € par billet, plafonnés à 6 € par commande ; early bird : -10 % sur le sous-total si l'achat a lieu au moins 30 jours avant le concert ; les frais ne sont jamais remisés. Voir aussi le contexte TicketRush.

Un mutant survivant vous dit : « aucun test ne remarquerait si cette ligne changeait ». Demandez-vous alors : laquelle des deux versions respecte la règle ?

Palier avancé · Au-delà du prix

Plus aucun survivant utile dans Pricing.cs ? Étendez Stryker aux autres règles métier :

dotnet stryker -m "**/Hold.cs" -m "**/Quota.cs"

Un mutant survit encore. Quelle frontière personne n'a-t-il testée ? Écrivez le test qui le tue.

Palier expert · Le mutation testing dans la stratégie

Certains mutants ne valent pas un test : le texte d'un message d'erreur, par exemple. Excluez-les dans stryker-config.json. Fixez ensuite un seuil break qui ferait échouer le build, et décidez à quel étage de la CI lancer Stryker. Écrivez ces trois choix comme vous les justifieriez dans une stratégie de test.

Palier bonus · Une nouvelle règle en TDD, avec ou sans IA

Le métier demande une remise de groupe : à partir de 5 billets dans la commande, -5 % sur le sous-total. Elle ne se cumule pas avec l'early bird : on applique la plus avantageuse des deux. Les frais ne sont jamais remisés.

  1. Rouge. Écrivez d'abord les tests de cette règle, vous-mêmes ou avec l'IA. Pensez aux frontières : 4 et 5 billets, early bird seul, groupe seul, les deux à la fois. Lancez-les : ils doivent échouer. Committez-les.
  2. Vert. Implémentez la règle dans Pricing.cs, vous-mêmes ou avec l'IA, sans toucher aux tests. Vérifiez avec git diff HEAD -- tests/ : rien ne doit avoir bougé.
  3. Contrôle. Relancez dotnet stryker. Le score a-t-il baissé ? Si un mutant survit dans votre nouveau code, vos tests ne décrivaient pas toute la règle.

Pour le bilan : qui a écrit les tests, qui a écrit le code, et qu'est-ce qui vous prouve que la règle est bien respectée ?

4. Débrief (5 min)

Les trois meilleurs scores expliquent leur méthode en deux minutes. À titre de repère, la branche lab-2-solution atteint 87,5 % : les seuls mutants survivants modifient des messages d'erreur.

À retenir : la couverture dit quelles lignes ont été exécutées, pas ce qui a été vérifié. Un test sans assertion précise couvre tout et ne prouve rien. Quand l'IA écrit vos tests, le mutation testing devient votre contrôle qualité.
