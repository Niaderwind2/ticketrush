Un agent IA arrêté par la CI

On demande à un agent de code d'ajouter une fonctionnalité. Le code a l'air correct. Qui l'empêche de casser la production ? Les tests, à condition qu'ils soient au bon étage.

La CI de TicketRush

ÉtageQuandBudgetBloque le merge ?
1. Tests unitairesÀ chaque push< 2 minOui
2. Tests d'intégration (PostgreSQL dans un conteneur)À chaque push et en pull request< 5 minOui
3. Mutation testingChaque nuit, ou à la demande< 30 minNon : alerte et rapport

Le fichier : .github/workflows/ci.yml dans le dépôt.

La démo

La demande faite à l'agent : « Pendant l'ouverture des ventes, la base est saturée. Le calcul du quota fait une requête SQL à chaque réservation : optimise-le. »

  1. L'agent ajoute un cache en mémoire de 5 minutes sur le nombre de billets de chaque client. C'est une optimisation classique, et le code est propre.
  2. Il lance les tests unitaires : tout est vert. Normal, ils utilisent un mock du repository.
  3. La pull request déclenche la CI. L'étage 2 échoue sur Le_quota_de_6_billets_tient_quand_les_requetes_arrivent_sur_deux_instances : avec deux instances de l'API, chacune a son propre cache, et un client obtient un septième billet.
  4. On lit l'échec ensemble. Le test d'intégration a joué le rôle de la règle que l'agent ne connaissait pas : en production, l'API tourne sur plusieurs instances.

La branche demo-agent du dépôt contient ce changement, et sa pull request montre la CI en échec.

Discussion

  • Quels tests doivent bloquer le merge ? Lesquels peuvent tourner la nuit ?
  • Si votre pipeline dure 25 minutes, que font les développeurs ? Et un agent ?
  • Quand un agent écrit le code et les tests, qui écrit les tests qui jugent l'agent ?

Les tests sont la spécification exécutable. Un agent IA ne connaît pas vos règles métier ni vos incidents passés. Vos tests, si.
