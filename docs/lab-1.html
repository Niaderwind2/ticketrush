Lab 1 : ce que le mock ne voit pas

Les tests du service de réservation passent tous. Ils utilisent des mocks. On va montrer qu'ils ne peuvent pas voir la double vente, la prouver avec un vrai PostgreSQL, puis la corriger en TDD.

Objectif : un test qui échoue tant que deux clients peuvent obtenir la même place, et qui passe une fois le défaut corrigé. Choisissez votre piste : code (C#) ou boîte noire (n'importe quel langage).

Préparation (5 min)

git pull
docker compose up -d --build --wait     # l'API répond sur http://localhost:8080
dotnet test                             # piste code : tout est vert

Piste code (C#)

Socle · 1. Lire les tests existants (10 min)

Ouvrez tests/TicketRush.UnitTests/ReservationServiceTests.cs. Tous les tests passent.

  • Que remplace Substitute.For<IReservationRepository>() ?
  • Dans Refuse_une_place_deja_reservee, qui décide que la place est prise : le code, ou le test ?

Socle · 2. Rouge : écrire le test qui prouve la double vente (20 min)

Créez tests/TicketRush.IntegrationTests/ConcurrencyTests.cs. Inspirez-vous de ReservationRepositoryTests.cs : la classe PostgresFixture démarre un vrai PostgreSQL dans Docker.

Le test : 20 clients réservent la même place en même temps. Attendu : 1 succès, 19 SeatAlreadyTakenException.

[Fact]
public async Task Vingt_clients_sur_la_meme_place_une_seule_reservation_reussit()
{
    var service = new ReservationService(
        new PgReservationRepository(pg.DataSource),
        Substitute.For<IPaymentGateway>(),
        TimeProvider.System);

    var attempts = Enumerable.Range(1, 20)
        .Select(i => Task.Run(() => service.ReserveAsync(
            new ReserveCommand(pg.EventId, 100, $"client-{i}", Tariff.Plein))))
        .ToArray();
    await Task.WhenAll(attempts.Select(t => t.ContinueWith(_ => { })));

    Assert.Equal(1, attempts.Count(t => t.IsCompletedSuccessfully));
}

Lancez-le plusieurs fois avec dotnet test tests/TicketRush.IntegrationTests. Il doit être rouge. S'il est parfois vert, notez-le : c'est le palier avancé.

Socle · 3. Vert : corriger (20 min)

Le service fait « je vérifie que la place est libre, puis j'insère ». Entre les deux, un autre client peut passer. Où placer la garantie d'unicité pour qu'elle tienne quelle que soit la concurrence ?

Indices progressifs, à ouvrir seulement si vous bloquez plus de 10 minutes :

Indice 1

Le code applicatif ne peut pas garantir l'unicité seul : plusieurs instances de l'API peuvent tourner en même temps. Qui voit toutes les requêtes ?

Indice 2

PostgreSQL sait garantir l'unicité avec un index unique. Il peut même être partiel : uniquement sur les réservations actives (WHERE status IN ('Held', 'Paid')).

Indice 3

Ajoutez l'index dans schema.sql, puis interceptez l'erreur PostgresErrorCodes.UniqueViolation dans PgReservationRepository.InsertAsync pour la traduire en SeatAlreadyTakenException.

Socle · 4. Refactor et bilan (5 min)

Tous les tests sont verts ? Relisez votre correction. Puis répondez : quel test aurait dû exister dès le départ, et à quel étage du pipeline ?

Palier avancé · Rendre le test fiable

Un bug de concurrence ne se montre pas à chaque exécution. Votre test est-il rouge à chaque fois avant la correction ? Rendez-le fiable : libérez tous les clients au même instant (une barrière avec TaskCompletionSource), et répétez l'expérience sur plusieurs places ([Theory]). Puis faites la même chose pour le double clic : 5 requêtes simultanées avec la même clé d'idempotence ne doivent créer qu'une réservation.

Palier expert · Tests par propriétés

Ajoutez FsCheck (dotnet add tests/TicketRush.UnitTests package FsCheck.Xunit) et écrivez des propriétés sur Pricing : « le total n'est jamais négatif », « les frais ne dépassent jamais 6 € », « ajouter un billet n'a jamais fait baisser le total ». Comparez avec des tests par exemples : qu'est-ce que chaque approche trouve que l'autre ne trouve pas ?

Piste boîte noire (tous langages)

Même objectif, sans toucher au C# : prouvez la double vente par l'API HTTP.

Socle · Écrire le test de double vente

Lancez 20 requêtes POST /events/1/reservations au même instant sur la même place, puis comptez les réponses 201. Attendu : exactement une.

Deux exemples complets sont fournis, à lire puis à réécrire dans votre langage :

Palier avancé · Le double clic

Envoyez 5 requêtes simultanées avec le même en-tête Idempotency-Key. Combien de réservations sont créées ? Vérifiez avec GET /admin/stats.

Palier expert · Relire la correction

Faites équipe avec un binôme de la piste code : relisez sa correction et vérifiez que votre test passe dessus (git checkout lab-1-solution puis docker compose up -d --build).

À retenir

Un mock ne vérifie que ce que vous avez supposé. Les défauts de concurrence, de contraintes et de transactions n'existent qu'avec la vraie dépendance. Testcontainers rend ce test aussi simple à lancer qu'un test unitaire.
